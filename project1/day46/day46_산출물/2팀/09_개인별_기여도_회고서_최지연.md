## 2. 기술적으로 설명할 수 있는 내용

- **사용한 핵심 기술 및 선택 이유**
  - **faster-whisper base (cpu, int8):** 무료 서버에서도 한 문장을 1초 안팎에 처리한다. small은 더 정확하지만 메모리와 시간이 2~3배라 배포 안정성을 우선했다.
  - **edge-tts (ko-KR-SunHiNeural):** 무료이고 자연스러운 한국어 음성이다. 생성 음성을 STT로 되돌려 검증했을 때 CER 13.7%였다.
  - **CER(글자 단위) 중심 평가:** 한국어는 띄어쓰기 오류가 잦아 WER(어절)이 과하게 나온다. 공백을 제외한 글자 단위 정렬(jiwer)로 S/D/I를 산출했다.
  - **Neon PostgreSQL:** 클라우드 DB라 팀원 모두 같은 데이터를 보고, 배포 후에도 그대로 쓸 수 있다. 오류는 `practice_runs`(요약)와 `error_items`(글자별)로 나눠 저장했다.
  - **Streamlit 기본 기능 위주 UI:** CSS 파일 의존을 없애 경로·버전 오류를 줄이고, 테마는 `config.toml` 한 곳에서 관리했다.

- **가장 어려웠던 문제와 원인**
  1. **전처리 효과 지표가 실측이 아니었다.** 팀원 스크립트가 원본 CER에서 2.5%p·5%p를 일괄로 빼는 시뮬레이션이었다. 그 결과 "잡음 제거가 가장 효과적"이라는 잘못된 결론이 나와 있었다. 전처리는 소리에 하는 작업이라 텍스트만으로는 효과를 잴 수 없었다.
  2. **Whisper가 학습자 오류를 바르게 고쳐 인식했다** (싶어여 → 싶어요, 약곡이 → 약국이). 틀린 발음을 맞다고 판정하는 미탐률이 25%였다.
  3. **잡음 제거가 오히려 환각을 키웠다.** 소리를 깎은 빈 구간을 Whisper가 반복 문장으로 채워, 삽입 오류가 29건에서 111건으로 늘었다. 키보드 소리처럼 순간적으로 튀는 소음은 잡음 제거로 지워지지 않았다.

- **직접 구현한 해결 과정**
  - 원본 녹음에 전처리를 실제로 적용하고 Whisper로 다시 전사하는 실험 코드를 만들어 4조건 CER을 실측했다. 결과: 무음 제거 −20%p 개선, 잡음 제거 악화.
  - 일부러 틀리게 읽은 녹음 10개를 직접 만들어 정답 녹음과 짝지었다. 이 쌍으로 혼동 행렬(TP/FP/FN/TN)과 오탐률·미탐률을 산출했다.
  - 권고안: **앱에는 무음 제거만 적용**하고, CER 100% 초과나 3회 이상 반복이 나오면 재녹음을 안내한다. 추가로 Whisper small 비교를 검토한다.
  - 정답 문장 표기 오류("어디에요" → 표준어 "어디예요")가 감점을 만든 사례를 찾아 seed 데이터 수정을 제안했다.

- **STT/TTS 파이프라인 이해 내용**
  ```
  녹음(WAV/마이크) → 16kHz 모노 변환 → 전처리(무음 제거) → Whisper 전사
  → 정규화(문장부호·공백 제거) → 글자 정렬(S/D/I) → CER·점수·피드백
  → DB 저장(practice_runs + error_items) → 결과 화면 / 정답 음성(TTS) 재생
  ```
  - 처리 시간 비중: STT 63%, TTS 37%, 전처리·채점 0.2% 미만. 속도 개선은 STT 설정과 TTS 캐싱이 핵심이다.
  - 점수는 **발음 정확도가 아니라 "STT 전사 일치도"**이다. 피드백 문구와 발표에서 이 점을 구분해 표기했다(NFR-05).
  - TTS 캐시가 모든 문장을 같은 파일(`current_target.wav`)에 덮어써, 다른 문장 음성이 재생될 수 있는 버그를 발견했다.

## 3. 협업·코드 리뷰

- **본인이 리뷰한 코드**
  - `export_whisper_validation.py` (전처리 비교): 시뮬레이션 값을 찾아내고 실측 방식으로 재작성했다.
  - `src/core.py` (점수·등급): 등급 경계에서 점수가 왜곡되는 문제(I-01)를 수정했고, 피드백 문구 표현(I-02)을 검토했다.
  - `app/apps/app_practice.py`·`src/db.py`: 오류 위치가 DB에 저장되지 않던 누락을 찾아 저장 함수를 추가했다.
  - `app_history.py`: 통합 브랜치에서 홈 화면 코드로 덮어써진 것을 발견하고 원본 커밋으로 복구했다.
  - `src/tts.py`: 캐시 파일 덮어쓰기 버그를 지적했다.

- **다른 팀원으로부터 받은 피드백**
  - 관리자 화면: 정렬 기준, 표 글자 정렬 통일, 차트 안 수치 표시(10/28) → I-04로 등록하고 반영 일정을 잡았다.
  - "텍스트 정규화"와 "음성 전처리" 용어가 섞여 있다는 지적 → I-05로 정리하고, 실제 수행 범위만 기재하도록 문서를 수정했다.

- **역할 분담의 적절성**
  - 5인 체제(PM·데이터·AI·DB·UI)로 영역은 명확했다. 다만 통합 시점에 같은 파일(app.py, app_history.py)을 여러 명이 수정해 덮어쓰기가 발생했다. "남의 파일은 담당자 동의 후 수정" 규칙(NFR-08)을 중반 이후 도입했다.
  - 평가·실험은 담당이 나뉘어 있어 결과 검증 책임이 불분명했다. 팀장이 실측 재검증을 맡아 공백을 메웠다.

## 5. 다음 프로젝트 개선점

1. **지표는 처음부터 실측 파이프라인으로 만든다.** 원본 녹음 저장과 재측정 스크립트를 D1에 설계해, 시뮬레이션 값이 보고서에 들어가는 일을 막는다.
2. **평가 데이터를 "정답·오답 쌍"으로 처음부터 수집한다.** 정답 녹음만으로는 오탐·미탐을 측정할 수 없었다. 녹음 가이드(파일명 규칙, 조용한 환경, 키보드 소음 금지)를 먼저 배포한다.
3. **통합은 PR 리뷰를 필수로 한다.** 웹에서 직접 업로드·삭제하는 커밋을 줄이고, `integration` 병합 전 1인 이상 리뷰와 로컬 실행 확인을 규칙화한다.
4. **배포를 앞당긴다.** D5 안에 Streamlit Cloud 배포 주소를 만들어, 실제 사용자 테스트와 처리 시간 측정을 배포 환경에서 반복한다.
5. **모델 선택을 데이터로 결정한다.** Whisper base와 small의 정확도·속도를 같은 녹음으로 비교한 뒤 확정한다.
